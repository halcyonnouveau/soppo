# Plan: Import/Package System & Go Interop

## Overview

Design and implement Soppo's import/package system with seamless Go interoperability:
- Soppo code can import Go packages (types auto-extracted from Go source)
- Go code can import Soppo packages (via generated `.go` files in `gen/`)

## Design Decisions

### 1. Module System: Use go.mod
Soppo projects live inside Go modules. No separate `soppo.mod` - leverage existing Go tooling.

**Rationale:** Simpler integration, `go get` just works, pkg.go.dev indexing, no new infrastructure needed.

### 2. Shared Lexer, Separate Go Extractor
Soppo and Go parsing share the lexer but have separate parsing logic:

```rust
// Soppo - full AST for compilation
mod parser;       // existing parser

// Go - lightweight signature extraction
mod go_extract;   // new, uses same lexer, no full AST
```

**Go extractor:**
- Reuses `lexer.rs` tokens
- Extracts signatures directly into `GoPackage` struct (no AST)
- Pre-scans for `// soppo:enum` markers before lexing
- Handles Go-only constructs (interfaces, type aliases) without polluting Soppo parser

### 3. Go Multi-Return & Error Handling

Soppo supports Go's multi-return directly with the `?` operator for error handling.

#### Error Handling with `?`

For `(T, error)` returns, use `?` to auto-return on error:
```soppo
func process() (Config, error) {
    data := readFile("config.json") ?
    port := parsePort(data) ?
    return Config{port: port}, nil
}
```

With custom error wrapping:
```soppo
func process() (Config, error) {
    data := readFile("config.json") ? {
        return Config{}, fmt.Errorf("read failed: %v", err)
    }
    return Config{port: 8080}, nil
}
```

#### Multi-Value Returns

Soppo supports Go-style multi-value returns natively:
```soppo
func divide(a int, b int) (int, int) {
    return a / b, a % b
}

func main() {
    quot, rem := divide(10, 3)
}
```

No wrapper types needed - transpiles directly to Go.

### 4. Nil Safety

Soppo uses flow-sensitive nil tracking. Go allows nil dereference (crashes at runtime), but Soppo catches it at compile time:

```soppo
user := findUser(1)       // *User, may be nil
fmt.Println(user.Name)    // ERROR: user may be nil

if user != nil {
    fmt.Println(user.Name)  // OK: compiler knows non-nil here
}
```

### 5. Module Version Resolution
Shell out to `go list -m -json` to resolve module versions rather than parsing go.sum ourselves. Uses Go's battle-tested resolution logic.

### 6. Project Structure
```
project/
├── go.mod                    ← Go module definition
├── cmd/
│   └── myapp/main.sop        ← Soppo source (Go ignores .sop)
├── pkg/
│   └── util.sop
└── gen/                      ← Generated Go (committed to git)
    ├── cmd/
    │   └── myapp/main.go
    └── pkg/
        └── util.go
```

- Soppo source lives in conventional Go locations (`cmd/`, `pkg/`, etc.)
- Generated Go mirrors structure under `gen/`
- Go ignores `.sop` files, only compiles `.go` files
- Generated files are committed for seamless Go consumption

### 7. Import System

**All imports are Go imports** - no special syntax needed:
```soppo
import "fmt"                                      // Go stdlib
import "github.com/user/project/gen/pkg/util"     // Local Soppo package
import "github.com/other/soppo-lib/gen/pkg"       // External Soppo lib
import "github.com/other/golib"                   // External Go lib
```

Import paths always point to Go code. Type information is extracted separately.

### 8. Type Extraction (Two Sources)

| Import Type | Code Location | Types From |
|-------------|---------------|------------|
| Local Soppo | `gen/pkg/*.go` | `pkg/*.sop` (Soppo source) |
| External | `$GOMODCACHE/.../*.go` | Same `.go` files (parse Go) |
| Go stdlib | `$GOROOT/src/*.go` | Same `.go` files (parse Go) |

**Resolution logic:**
```
import "github.com/user/project/gen/pkg/util"
  → Starts with current module + "/gen/"?
  → Yes → Strip "gen/", look for pkg/util/*.sop
  → Found → Use Soppo source for types (full semantics)
  → Not found → Parse Go files (auto-extract types)
```

### 9. Preserving Soppo Semantics in Generated Code

Add marker comments so external Soppo libs retain enum semantics:

```go
// Code generated by soppo. DO NOT EDIT.

/*soppo:enum
Result[T any, E any] {
    Ok T
    Err E
}
*/
type Result[T any, E any] interface {
    isResult()
}
// ... rest of enum implementation
```

When parsing external Go code:
1. Look for `/*soppo:enum` block comments
2. Parse original Soppo syntax from comment
3. Reconstruct full enum semantics (exhaustiveness, pattern matching)
4. No marker = treat as regular Go interface

**Benefits:**
- External Soppo libs work like local ones
- No manual type declarations needed
- Graceful fallback for pure Go code

## Implementation Phases

### Phase 1: Multi-file Compilation

**Current:** Single file in → single file out
**Goal:** Directory/project compilation

#### 1.1 CLI Changes
**File:** `src/main.rs`

```
soppo build [path]           # Build project (default: current dir)
soppo build --output <dir>   # Custom output directory (default: gen/)
soppo check [path]           # Type-check without codegen
```

**Logic:**
1. Find all `.sop` files in project (excluding gen/)
2. Parse each file
3. Build dependency graph from imports
4. Type-check in dependency order
5. Generate Go files to `gen/` mirroring source structure

#### 1.2 Project Discovery
**File:** `src/project.rs` (new)

```rust
struct Project {
    root: PathBuf,           // Directory containing go.mod
    module_path: String,     // e.g., "github.com/user/project"
    source_files: Vec<PathBuf>,
    output_dir: PathBuf,     // Default: root/gen/
}

impl Project {
    fn discover(start: &Path) -> Result<Project>;  // Walk up to find go.mod
    fn find_sources(&self) -> Vec<PathBuf>;        // Find all .sop files
    fn output_path(&self, source: &Path) -> PathBuf; // Map source → gen path
}
```

### Phase 2: Import Resolution

#### 2.1 Import Categories
**File:** `src/resolve.rs` (new)

Three kinds of imports:
1. **Local Soppo** - another `.sop` file in this project
2. **Go stdlib** - `"fmt"`, `"net/http"`, etc.
3. **External Go** - `"github.com/other/pkg"`

```rust
enum ImportKind {
    LocalSoppo { source_path: PathBuf },
    GoStdlib { package: String },
    ExternalGo { module_path: String },
}

fn resolve_import(import_path: &str, project: &Project) -> Result<ImportKind>;
```

#### 2.2 Resolution Logic
```
import "X"
  → Does gen/X/*.sop exist locally? → LocalSoppo
  → Is X a known Go stdlib package? → GoStdlib
  → Otherwise → ExternalGo
```

#### 2.3 Package Exports
**File:** `src/module.rs` (expand existing)

Track what each package exports:
```rust
struct PackageExports {
    types: HashMap<String, TypeDef>,
    functions: HashMap<String, FuncSignature>,
    constants: HashMap<String, Type>,
}
```

When importing a package, load its exports into scope.

### Phase 3: Go Source Parsing

#### 3.1 Go Extractor
**File:** `src/go_extract.rs` (new)

Lightweight extractor using shared lexer:

```rust
struct GoPackage {
    functions: HashMap<String, FuncSignature>,
    types: HashMap<String, TypeDef>,
    constants: HashMap<String, Type>,
    soppo_enums: HashMap<String, EnumDef>,  // From marker comments
}

impl GoExtractor {
    fn new(source: &str) -> Self;
    fn extract(&mut self) -> Result<GoPackage>;
}
```

**Process:**
1. Pre-scan source for `/*soppo:enum` block comments
2. Lex using shared `lexer.rs`
3. Extract signatures (no full AST needed)
4. Handle Go-only: interfaces, type aliases, multiple declarations
5. Filter to exported names only (capitalized)

#### 3.2 Source Location
**File:** `src/go_locate.rs` (new)

Find Go source for a package:
```rust
fn locate_go_source(import_path: &str) -> Result<PathBuf> {
    // 1. Stdlib: $GOROOT/src/<path>
    // 2. Module cache: $GOMODCACHE/<module>@<version>
    // 3. Local: relative to go.mod
}

fn get_goroot() -> PathBuf;      // from `go env GOROOT`
fn get_gomodcache() -> PathBuf;  // from `go env GOMODCACHE`
```

#### 3.3 Caching
**File:** `src/go_cache.rs` (new)

Cache parsed Go packages to avoid re-parsing:
```rust
struct GoCache {
    packages: HashMap<String, GoPackage>,
}

impl GoCache {
    fn get_or_parse(&mut self, import_path: &str) -> Result<&GoPackage>;
}
```

#### 4.1 Build Order

**File:** `src/infer.rs` (modify)

### Phase 5: Code Generation Updates

#### 5.1 Output Structure
**File:** `src/codegen.rs` (modify)

- Add `// Code generated by soppo. DO NOT EDIT.` header
- Output to `gen/` directory mirroring source structure
- Handle package declaration based on directory

#### 5.2 Import Rewriting
Soppo imports may need adjustment for generated Go:
```soppo
// Soppo source
import "myproject/pkg/util"  // Actually refers to Soppo package
```
```go
// Generated Go
import "myproject/gen/pkg/util"  // Points to generated location
```

## Example Workflow

```bash
# Project structure
myproject/
├── go.mod                 # module github.com/user/myproject
├── cmd/app/main.sop
├── pkg/util/helper.sop
└── gen/                   # generated (committed to git)
    ├── cmd/app/main.go
    └── pkg/util/helper.go
```

```soppo
// cmd/app/main.sop
package main

import "fmt"                                        // Go stdlib (auto-parsed)
import "github.com/user/myproject/gen/pkg/util"     // Local Soppo package (via gen/)

func main() {
    msg := util.Hello("world")
    fmt.Println(msg)
}
```

```bash
# Build
$ soppo build
Parsing Go: fmt (from $GOROOT/src/fmt)
Compiling: pkg/util/helper.sop → gen/pkg/util/helper.go
Compiling: cmd/app/main.sop → gen/cmd/app/main.go

# Run with Go
$ go run ./gen/cmd/app

# Another Go project can import the generated code
import "github.com/user/myproject/gen/pkg/util"
```
